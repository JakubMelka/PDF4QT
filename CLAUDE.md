# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

PDF4QT is a C++20 / Qt 6 PDF library plus a family of desktop applications (editor, viewer, page master, diff, launch pad) and a command line tool. Single author project (Jakub Melka), MIT licensed since April 2025.

## Working on GitHub issues

When a GitHub issue is fixed or an enhancement implemented, **the issue must be recorded in [RELEASES.txt](RELEASES.txt)** under the `CURRENT:` section at the top of the file, in the form:

```
 - Issue #NNN: <issue title as it appears on GitHub>
```

Newest issues go first inside `CURRENT:`; the section is renamed to a version line (`V: 1.6.0.0 14.6.2026`) at release time. Commit messages follow the same convention: `Issue #NNN: <issue title>`.

## Build and test

Changes are expected to be built and tested: after editing code, build the affected targets and run the unit tests, and report the result (see [AGENTS.md](AGENTS.md)). A change is not finished until it compiles warning-free and the relevant tests pass.

Configure (vcpkg toolchain is required; Qt 6.9+):

```
cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
```

Useful options: `PDF4QT_BUILD_ONLY_CORE_LIBRARY` (skips every GUI target and the apps), `PDF4QT_BUILD_TESTS` (ON by default), `PDF4QT_QT_ROOT` (needed when installing Qt dependencies), `PDF4QT_INSTALL_TO_USR`. On Linux set `VCPKG_OVERLAY_PORTS` to `vcpkg/overlays/linux:vcpkg/overlays/general` to avoid the incompatible libpng crash.

On this machine there is an existing Ninja + MSVC debug tree at `build/msvc2022_debug` (Qt 6.9.0 at `E:/Programming/Qt/6.9.0/msvc2022_64`). When that tree is missing, use the Qt Creator tree `build/Desktop_Qt_6_11_2_MSVC2026_64bit_Release` (Release, Qt 6.11.2, `VCPKG_MANIFEST_INSTALL=OFF` - after a change of [vcpkg.json](vcpkg.json) run `vcpkg install --x-manifest-root=. --x-install-root=<build>/vcpkg_installed --overlay-ports=vcpkg/overlays/general` by hand). Build it by writing a `.bat` to the scratchpad (nested quotes get mangled otherwise) that calls `vcvars64.bat`, `cd /d` into the build dir and runs `ninja <target>`.

Tests touching `QRawFont` or any GUI type must use `QTEST_MAIN` (QGuiApplication), not `QTEST_APPLESS_MAIN`.

## Architecture

### Module layering

Strictly layered; each layer is a shared library that only depends on the ones above it.

- **[Pdf4QtLibCore/](Pdf4QtLibCore/)** — the PDF engine. No Qt Widgets dependency (Core, Gui, Svg, Xml, Network only), so it can be built stand-alone via `PDF4QT_BUILD_ONLY_CORE_LIBRARY`. Parsing, object model, rendering, fonts, color management, encryption, signatures, forms, annotations, optimization, XFA.
- **[Pdf4QtLibWidgets/](Pdf4QtLibWidgets/)** — widget layer: the page draw widget, draw space controller, asynchronous compilers, tool framework, annotation/form widget managers, page content editor tools.
- **[Pdf4QtLibGui/](Pdf4QtLibGui/)** — the application shell shared by Editor and Viewer: main windows, `PDFProgramController`, `PDFActionManager`, settings, sidebar, dialogs, text-to-speech.
- **[Pdf4QtLibFluent/](Pdf4QtLibFluent/)** — look of the user interface of the GUI overhaul (see *Fluent style* below). It depends only on Qt (Core, Gui, Widgets, Svg), not on Pdf4QtLibCore, so every application can link it; no application does yet and the library is not installed.
- **[Pdf4QtLibMcp/](Pdf4QtLibMcp/)** — the MCP server of the new application (step 7, design [GUI_overhaul/newapp_mcp.md](GUI_overhaul/newapp_mcp.md)): transport and protocol only, no document logic. Links Pdf4QtLibCore (only for `PDFOperationControl` - a `PDFMcpCall` is the cancellation of the Core functions it runs), QtCore and QtNetwork, no Gui / Widgets; not installed in phase 1. Streamable HTTP on one endpoint `/mcp` with its own strict HTTP/1.1 parser `PDFMcpHttpParser`, both protocol eras at once (owner decision O26: the stateless revision 2026-07-28 - `server/discover`, `subscriptions/listen`, `input_required` with a sealed `PDFMcpRequestState`, the tasks extension - and the legacy 2025-11-25 / 2025-06-18 with `initialize` and `Mcp-Session-Id`). Threads: the sockets live in a fixed pool of 4 I/O threads (`PDFMcpIoThreads`, `PDFMcpConnection` per socket), the listeners and `PDFMcpDispatcher` (token, Host / Origin, era, headers, sessions, assistants, listen streams, tasks, rate limits, the list methods from the immutable `PDFMcpCatalog` snapshot) in one control thread (`PDFMcpControl`); the abstract `PDFMcpHost` is called only in its own (GUI) thread by queued invocations, and nobody blocks (no lock across threads, a result for a dead host or connection is dropped). `PDFMcpServer` (GUI thread) owns the threads; its `stop()` is synchronous and runs before the host is destroyed. JSON is parsed by `QJsonDocument` behind `PDFMcpJsonScanner` (one pass before it: size, depth, members, duplicate keys, UTF-8, the exact top-level id; differentially fuzzed against Qt), read by the strict `PDFMcpJsonReader` and written by the ordered `PDFMcpJsonWriter` (deterministic schemas of `PDFMcpSchemaBuilder`, no `oneOf` / `$ref`); every limit is in `PDFMcpLimits`, every error code in `PDFMcpErrorCodes`. No lambdas and no anonymous namespaces; export `PDF4QTLIBMCPSHARED_EXPORT`, prefix `PDFMcp`.
- **[Pdf4QtLibApp/](Pdf4QtLibApp/)** and the executable **`PDF4QT`** ([Pdf4QtApp/](Pdf4QtApp/)) — the new unified application (plan [GUI_overhaul/newapplication.md](GUI_overhaul/newapplication.md)), being built; not installed in phase 1. `sources/storage` — one SQLite database in WAL per user instead of QSettings (`PDFDatabase`: one connection per thread, migrations, damaged / newer / unopenable files, portable memdb; one file per schema version `<data>/pdf4qt-<schema>.db` - owner decision O19, `PDFDatabaseFiles`: a missing file is created from a copy of the newest older file by the backup API, migrated in a temporary file under a lock and renamed, the older file is never written and never deleted automatically; rules of migrations in newapp_storage.md 5 - a released migration is never changed, columns are never renamed or dropped, a new column has a default, unknown values are read as defaults, SQL always names its columns, a breaking change is a new schema version; `PDFDatabaseNotifier`: change log triggers + `PRAGMA data_version`; repositories), `sources/core` — `PDFSettingDefinition` registry, `PDFAppCommandRegistry`, `PDFAppCommandLine`, forwarding of files to a running instance (`PDFAppInstanceGuard`, `QLocalServer`), `PDFAppLog`, `PDFAppContext`, `PDFAppWindowFactory`, `PDFAppLocale` (owner decision O17: dates, times, file sizes and numbers shown by the application are formatted by its functions - `formatDate`, `formatDateTime`, `formatDataSize`, `formatNumber`, `getUiLocale()`, the hybrid time of recent activity of O25 `formatRecentTime` ("5 minutes ago", updated once a minute by the shared `PDFAppMinuteTicker` of the context, to which a page subscribes its widget) - in the language of the user interface, English until the translations of step 5, never by `QLocale()` / `QLocale::system()`; ### Document model

`PDFObject` ([pdfobject.h](Pdf4QtLibCore/sources/pdfobject.h)) is an immutable, implicitly-shared variant of the eight PDF object types. `PDFDictionary` and `PDFArray` are immutable too (header and items in one allocation); build or modify them with `PDFDictionaryBuilder` / `PDFArrayBuilder` (`PDFDictionaryBuilder builder(*dictionary); builder.setEntry(...); PDFObject::createDictionary(std::move(builder))`), use `setFixedSize(n)` only when the number of items is known in advance. `PDFObjectStorage` holds all objects and is thread-safe for reading only. `PDFDocument` ([pdfdocument.h](Pdf4QtLibCore/sources/pdfdocument.h)) wraps the storage plus catalog and is **immutable** — every modification produces a new document.

Because of that, changes flow through `PDFModifiedDocument`, which carries the new document plus modification flags (`Reset`, `Annotation`, `FormField`, `PageContents`, …). Consumers use the flags to skip expensive rebuilds; when unsure, `Reset` is the conservative choice. Read values out of dictionaries with `PDFDocumentDataLoaderDecorator` rather than by hand — it has both defaulted and throwing accessors.

Writing/editing goes through `PDFDocumentBuilder` ([pdfdocumentbuilder.h](Pdf4QtLibCore/sources/pdfdocumentbuilder.h)). A large part of its API is generated from `generated_code_definition.xml` by the `CodeGenerator` app — regenerate rather than hand-editing those methods. `PDFDocumentWriter`, `PDFOptimizer`, `PDFDocumentSanitizer`, `PDFDocumentManipulator` and `PDFRedact` operate on the same builder-produced documents.

Errors are reported by throwing `PDFException` ([pdfexception.h](Pdf4QtLibCore/sources/pdfexception.h)); rendering errors are collected non-fatally through `PDFRenderErrorReporter`.

### Rendering pipeline

`PDFPageContentProcessor` ([pdfpagecontentprocessor.h](Pdf4QtLibCore/sources/pdfpagecontentprocessor.h)) is the single interpreter of page content streams — it decodes operators, maintains `PDFPageContentProcessorState` (the PDF graphic state) and calls virtual `performXxx` hooks. Everything that consumes page content derives from it:

- `PDFPainter` — draws directly onto a `QPainter` (basic transparency only).
- `PDFPrecompiledPageGenerator` → `PDFPrecompiledPage` — bakes the content into a replayable instruction list; this is what the viewer caches and "plays" for fast repaints.
- `PDFTransparencyRenderer` — full transparency groups, blend modes and spot colors, software rasterized.
- `PDFBLPainter` ([pdfblpainter.h](Pdf4QtLibCore/sources/pdfblpainter.h)) — Blend2D-backed `QPaintEngine` used as an alternative backend.
- `PDFTextLayoutGenerator`, `PDFPageContentEditorProcessor`, `PDFJavaScriptScanner`, image extraction — non-drawing consumers.

Add support for a new operator or graphic feature in the processor first, then in each derived painter that needs it.

Caches of data derived from a document are neither held by `PDFDocument` nor global. They are separate objects created at the place, where the pages are processed, and passed to the content processors: `PDFFontCache` and, next to it, `PDFICCProfileCache` ([pdfcolorspaces.h](Pdf4QtLibCore/sources/pdfcolorspaces.h), decoded ICC profiles of the color spaces; it is passed also to `PDFAbstractColorSpace::createColorSpace` and `PDFPattern::createPattern`, and it can be `nullptr`). Each of them belongs to a single version of the document - call `setDocument` for each new version. A content processor does not own the realized fonts it has used (a font removed from the font cache must be released): a font is held only while a text is drawn, and the painter paths of the glyphs are stored under the identifier of the outline (`PDFGlyphOutline::getId`, never used again), not under its address.

In the widget layer, `PDFDrawSpaceController` lays pages out in millimeters (zoom-independent, block based), `PDFDrawWidgetProxy` maps that device space to widget pixels, and `PDFAsynchronousPageCompiler` / `PDFAsynchronousTextLayoutCompiler` ([pdfcompiler.h](Pdf4QtLibWidgets/sources/pdfcompiler.h)) compile pages on worker threads into a size-limited cache. Long operations honor `PDFOperationControl` for cancellation and report through `PDFProgress`. Thread fan-out is centralized in `PDFExecutionPolicy` ([pdfexecutionpolicy.h](Pdf4QtLibCore/sources/pdfexecutionpolicy.h)) — use it instead of spawning threads ad hoc.

### OCR

Specified by [OCR.md](OCR.md) (Czech), implementation report in [OCR_REPORT.md](OCR_REPORT.md). The engine independent part lives in Pdf4QtLibCore (`pdfocr*.h`): data model in canonical unrotated PDF user space (`PDFOCRPageResult`, quads ordered bottom-left, bottom-right, top-right, top-left of the reading direction), `PDFOCREngine` / `PDFOCREngineFactory` / `PDFOCREngineRegistry` (engines return raw pixel-space output, `PDFOCRPagePreparer` maps it back through `pageToRaster * rasterToEngine`), `PDFOCRPagePreparer` (analysis: `textRectangles` of the existing digital / foreign invisible text, a scan with any such text is `Mixed` and needs a decision; rasterization honors `/UserUnit` and the engine dimension limit; the page fingerprint `PDF4QT-OCR-PAGE-FINGERPRINT-2` covers the full raw streams of the resources, the annotations and the default optional content configuration, excluding only the verified own layer streams; overlapping inclusive regions with the same configuration are united), `PDFOCRJobController` (worker pool, one engine instance per worker, memory budget, cancellation), `PDFOCRSession` (results, corrections, undo/redo), `PDFOCRTextLayerWriter` (invisible text with an embedded glyphless font shared by the pages, the text origin lies on the line baseline and a negative `Ts` shifts the glyph boxes back onto the word geometry; foreign content is enclosed between `q` / `Q` isolation streams - shared when the foreign content is balanced, page specific with extra `ET` / `EMC` / `Q` closers otherwise, `computeContentBalance` / `validatePageContent` check the nesting by the lexer; own layer identified by the page `/PieceInfo /PDF4QT_OCR` - its references are untrusted input, the content and data streams are bound by `ContentHash` / `DataHash` (SHA-256 of the decoded streams) and the content must pass `isInvisibleTextStream`, a stream changed by another tool is foreign content: it is part of the fingerprint, never removed and `readLayer` returns nothing; `apply` refuses `reviewOnly` results and words colliding with `analysis.textRectangles`, and recomputes the exclusion flags from the current regions; `PDFPage::getContents()` is already dereferenced, use `getPageContentReferences`), `PDFOCRModelManager` (catalog with pinned checksums in [ocr/catalog/](ocr/catalog/), three profiles `fast` / `standard` / `best` = repositories tessdata_fast / tessdata / tessdata_best, iterate them with `PDFOCRConfiguration::getProfiles()`, built-in models in `ocr/tesseract/<profile>/` (only [fast](ocr/tesseract/fast/) is distributed, the larger profiles are downloaded by the user) - the model files are committed as one xz archive per model (`tessdata/<language>.tar.xz`, 13 MB instead of 35 MB) and CMake extracts them into `<build>/<PDF4QT_INSTALL_OCR_DIR>`, which is what is installed and what the OCR tests read; the catalog, the manifests, the licenses and the archives are generated by [ocr/tools/generate_catalog.py](ocr/tools/generate_catalog.py), `--fetch-builtin` restores a missing or damaged archive without the 3 GB cache, a run without it regenerates the catalog and caches all models (3 GB), `--<profile>-commit` moves a pinned commit, `--builtin-<profile>` changes a built-in set (then update [WixInstaller/Product.wxs.in](WixInstaller/Product.wxs.in) by hand); https downloads, imports, runtime sets built in place under the lock and published by `complete.json` written last - never renamed) and `PDFOCRProject`. The Tesseract adapter is the separate shared library [Pdf4QtOcrTesseract/](Pdf4QtOcrTesseract/) (option `PDF4QT_ENABLE_OCR`, define `PDF4QT_OCR_TESSERACT`), nothing else may include Tesseract or Leptonica headers. The dialogs (`PDFOCRDocumentDialog`, `PDFOCRLanguagesDialog`, `PDFOCRPageView`) are in Pdf4QtLibGui; the `.ui` files of the two dialogs are large, keep object names stable because the dialog test looks widgets up by name.

Extensions of [OCR_PLAN.md](OCR_PLAN.md) (chapter 10 of the report): `PDFOCRApplyProcessor` (`pdfocrapplyprocessor.h`) is the UI independent write transaction used by the dialog and the command line (verify fingerprints → compress images → write layer → strip conformance of a copy → validate → write copy); `PDFOCRImageCompressor` / `PDFOCRCompressionSettings` (`pdfocrcompression.h`, JBIG2 only as a generic region, never a symbol dictionary; lossy modes need the preview in the dialog and are not offered by the batch dialog); `PDFOCRTextLayerWriter::rebindFingerprints` rebinds an own layer when only the image encoding changed (also called by `PDFImageOptimizer`); `PDFOCRStructuredExporter` (`pdfocrexport.h`, coordinates of the visible page at the export DPI); `PDFOCRWord::inDictionary` + `PDFOCRReviewCriteria` (words outside the dictionary of the model need a review, default on, no extra dictionary library); `PDFOCRPreprocessing::perspective` (projective working raster, words converted back to parallelograms by `toParallelogram`); `PDFScanPreparation` (`pdfscanpreparation.h`, crop / split / deskew of the visible pages before OCR, wrapper streams, cloned page dictionaries sharing the content, the caller decides about pages with an own layer) with `PDFScanPreparationDialog`; `PDFOCRDocumentRunner` (`pdfocrdocumentrunner.h`, synchronous headless recognition with its own event loop - call it from a thread with an event dispatcher - and `processFile` for a single file) used by `PdfTool ocr` ([pdftoolocr.cpp](PdfTool/pdftoolocr.cpp), also `ocr-models`, never downloads without `--accept-download`) and `PDFOCRBatchDialog` (worker `QThread`). The OCR data root is shared by all PDF4QT applications: `PDFOCRModelManager::getApplicationDataRoot` maps the application name of organization `MelkaJ` to `PDF4QT Editor`, so PdfTool sees the models downloaded in the editor. PdfTool links `Pdf4QtOcrTesseract` only with `PDF4QT_ENABLE_OCR` and registers the engine in `main`.

### Fluent style

The design is the Figma file of the GUI overhaul, page *Widgets* (one section per family of controls; drawings and the *Geometry* lines are binding, the *Implementation* notes are guidance - several of them do not work against the Qt sources). [Pdf4QtLibFluent/](Pdf4QtLibFluent/) implements it:

- `PDFThemeColors` ([pdfthemecolors.h](Pdf4QtLibFluent/sources/pdfthemecolors.h)) - one enumeration value per variable of the Figma collection *Color* in the order of Figma, a theme is a table of their values (built-in `light` and `dark`, a new theme = `PDFThemeColors(id, name, scheme)` + `setColor` + `PDFThemeManager::registerTheme`). `PDFThemeManager` holds the active theme, widgets take colors from it and never by a cast of `QWidget::style()`.
- **The style never reads a QPalette.** The palette of the application is filled with the leak color `PDFThemeColors::getLeakColor()` (violet `#A000FF`), so a color of the system leaking into the user interface is seen at once; a violet pixel is a bug. Whatever Qt draws by itself from the palette of a widget (text of a line edit, rich text, calendar, status bar message, tooltip, message box) has a replacement in [pdffluentwidgets.h](Pdf4QtLibFluent/sources/pdffluentwidgets.h), [pdftooltip.h](Pdf4QtLibFluent/sources/pdftooltip.h), [pdfmessagebox.h](Pdf4QtLibFluent/sources/pdfmessagebox.h) - a subclass, which writes the colors of the theme into its own palette by `PDFThemeWidgetHelper::bindTextPalette`. Known gap: the HTML parser of Qt takes the color of a link (`<a href>`) from the palette of the application, not of the widget, so links of a rich text are violet.
- The library works only in the thread of the user interface: `PDFStylePainter`, `PDFComponentPainter`, `PDFPreviewPainter`, `PDFThemeIcons` and its icon engine read the active theme of `PDFThemeManager`, keep pixmaps in `QPixmapCache` and share the parsed SVG renderers (QObjects) and their other caches without a lock. A picture made by a worker thread (a rendered page) is passed to a component or a delegate as a pixmap / image, the drawing itself stays in the GUI thread.
- `PDFWidgetStyle : QCommonStyle` ([pdfwidgetstyle.h](Pdf4QtLibFluent/sources/pdfwidgetstyle.h)) dispatches each virtual function to the areas (`PDFWidgetStyleArea`, one file per family: `pdfwidgetstyle{buttons,inputs,ranges,menus,tabs,itemviews,containers}.cpp`), metrics and hints are in `pdfwidgetstylemetrics.cpp`, the state of the style (keyboard modality, focus frame, mnemonics after Alt, animations, preparation of popups, leak palette) in `PDFWidgetStyleImpl`. Nothing is drawn by `QCommonStyle`. Variants of a control are selected by dynamic properties (`PDFWidgetStyleProperties`: `primary`, `chip`, `segment`, `card`, `note`, `panel`, `canvas`, `documentTabs`, ...), set them by `PDFWidgetStyleProperties::set`.
- An area with the property `overlayScrollBars` has its scroll bars over the edge of the viewport (`PM_ScrollView_ScrollBarOverlap` = the extent 12, the layout reserves no width; the bar draws only its groove and slider): the page area of the application reaches into the padding of the workspace by the width of the bar, so the bar lies in the padding and the page keeps the width of the frames.
- The focus ring is shown only after the keyboard: fields draw it inside (also after a click), buttons get it from one overlaid `QFocusFrame` owned by the style, so a widget keeps the size of the shape of the design.
- Popups (menu, popup of a combo box, calendar, tooltip) are translucent windows with margins, where the shadow is drawn (`PDFWidgetStyleImpl::getPopupMargins`); their position is corrected at the show event (`movePopup`: the panel keeps the edge, by which Qt has anchored the window). The margins are not a part of the popup for the pointer: mouse events in them are passed to the menu or to the menu bar below them (`handlePopupMarginEvent`). The tooltip of Qt itself (`QTipLabel`: a rich text, `QToolTip::showText`) is an opaque panel, `QToolTip` has the palette of a text widget.
- Places, where Qt works against the design, are handled in the style and each of them is covered by `UnitTestsWidgetStyle` - check them after an upgrade of Qt: `QToolBarLayout` takes the positions of its items from transposed margins (`PDFWidgetStyleImpl::applyToolBarMargins`, `placeToolBarExtension`); `QTreeView` animates its branches from pictures filled by `palette().base()`, so the animation is turned off; `QTreeView::updateGeometries` resets the margins of the viewport (`PDFTreeView::updateGeometries`); `QHeaderView` derives the minimal section from `PM_HeaderMargin` (7 for vertical headers); editors of cells come from the default item editor factory of Qt (stock widgets drawn from the palette), so the style installs `PDFItemEditorFactory` as the default factory (unless the application has its own; `unpolish` restores the factory of Qt); the default `QStyledItemDelegate` places the editor into the rectangle of the text, so the frameless editor paints nothing and the view paints the edited cell (bg/surface and the one focus ring) below it - the style never replaces the delegate of a view (it would cut the editors and the connections of the application off the old delegate); `QProgressBar` has a minimal size hint higher than the bar (fixed thickness set in `polish`); `QPlainTextEdit` has no line height (`PDFPlainTextEdit` has its own document layout, `PDFTextEdit` keeps the lines of its fonts); a class font (`QApplication::setFont(font, className)`) is inherited by the children of the widget, so containers have none. The painter of a widget has the direction of the application (`QPainterState`), not of the widget, so a text aligned to the leading side of a widget is aligned absolutely (`PDFWidgetStyleImpl::getLeadingAlignment` / `getTrailingAlignment`).
- Icons of the system icon theme (`QIcon::fromTheme`, for example in the standard context menu of `QLineEdit`) are drawn by the platform from the palette (violet); `PDFWidgetStyleImpl::drawIcon` replaces them by the icon of the design (`PDFThemeIcons::getReplacementName`) or draws nothing. `PDFMessageBox` paints its own card (frameless translucent window, no title bar of the system) and covers its parent widget (or the widget of `setScrimTarget` - the application covers the body of its window below the top bar) by a scrim while it is shown, its title and text are plain texts; a dialog of the design is a message box with `setBadgeVisible(false)`, `addContent`, `addActionButton` (own row of buttons in the order of the design, they do not close it) and `setCardWidth`.
- Icons are the SVG files of Figma *Components / Icons* in [resources/icons](Pdf4QtLibFluent/resources/icons/) (unchanged; `PDFThemeIcons::getIcon(name)` returns an icon colored by the mode and by the theme; an icon is not scaled as a picture - its strokes keep 2 px at each size, as a resized instance in Figma), the font Inter is bundled in [resources/fonts](Pdf4QtLibFluent/resources/fonts/) (SIL OFL), sizes are in pixels.
- Components of the Figma page *Components* (spec, decisions and open findings in [GUI_overhaul/components.md](GUI_overhaul/components.md), [components_review.md](GUI_overhaul/components_review.md)) are widgets of the library, which draw themselves from the tokens. ### Plugins

Plugins are `SHARED` libraries deriving from `PDFPlugin` ([pdfplugin.h](Pdf4QtLibCore/sources/pdfplugin.h)), built into `${PDF4QT_PLUGINS_DIR}` and described by a sibling `<Name>Plugin.json` metadata file. They receive the widget and a `IPluginDataExchange` back-channel to the host application, and contribute `QAction`s. Existing ones: AudioBook, Dimensions, Editor, ObjectInspector, OutputPreview, Redact, Scanner, Signature, SoftProofing. A new plugin means a directory under [Pdf4QtEditorPlugins/](Pdf4QtEditorPlugins/), an `add_subdirectory` in its CMakeLists, the JSON descriptor, and an install rule.

## Conventions

- **CRLF line endings** for all source and text files (`.gitattributes` enforces `eol=crlf`); `.desktop` files stay LF.
- Every file starts with the MIT license header block (`Copyright (c) 2018-2026 Jakub Melka and Contributors`).
- No anonymous namespaces anywhere in the project. Functions are not free in a namespace: a file-local function is a static method of the class it serves or of a helper class defined in the `.cpp` (`<Class>Helper`, with a deleted constructor). Generic code goes to the generic helpers, not to a feature module: `PDFJsonHelper` ([pdfjsonhelper.h](Pdf4QtLibCore/sources/pdfjsonhelper.h)), `PDFGeometryUtils` and `PDFEnumerationNames` ([pdfutils.h](Pdf4QtLibCore/sources/pdfutils.h)), `PDFObjectUtils`, `PDFImageConversion`, `PDFFontCacheShrinkGuard` ([pdffont.h](Pdf4QtLibCore/sources/pdffont.h)); check them before writing a new utility.
- A `QPainterPath` (and its copies) is never used by more threads at once: its functions marked as const write into its data (bounding rectangles, data of the paint engine), and before Qt 6.10 the data are shared by the copies. Data shared by the threads are held as plain immutable data - glyphs of the realized fonts as `PDFGlyphOutline` ([pdffont.h](Pdf4QtLibCore/sources/pdffont.h)), from which each `PDFPageContentProcessor` creates its own paths (`getGlyphPath`).
- A nested class with default member initializers cannot be a default argument of a function declared inside its enclosing class (`const State& state = State()` - CWG 1397, GCC rejects it, MSVC does not): use an overload without the parameter.
- Lifetime of Qt objects: a slot of `QObject::destroyed` never calls a member of the sender (the destructor of the derived class has already run and its members are gone, but a `QPointer` to it is not cleared until `~QObject`) - it only forgets the pointer; a watched object of a subclass of QWidget, which a slot of `destroyed` or an event filter compares while it may be in its destructor, is held in `PDFWatchedPointer` (Pdf4QtLibFluent) - `isObject` compares the address, `QPointer<T>::data()` would cast the dying object to T (UBSan vptr); an object, which others watch, says it is going away from its own destructor while it is still whole. After every `Q_EMIT` and every call, which may run code of the application (a menu, a dialog, a callback), the code must survive the deletion of `this` and of the objects it uses: guard them by `QPointer` before and check it after. A slot never deletes the sender synchronously (`deleteLater`). Every connection has a context object (the receiver of the member-function slot), so it is cut when the receiver dies. A widget with nested objects, popups or watched objects has a test, which deletes them in every order (parent first, child first, from inside of its own signal, with a popup open). **Every widget of `Pdf4QtLibFluent` has a live sample on a page of the gallery**: `UnitTestsFluentLifetime` takes every widget of every page and destroys it in every order and situation, so a new widget is covered just by its sample (a child the application must not delete - a part of a Qt widget - is excluded by `WidgetCatalog`; what an application does with the widget, which the generic input cannot do - a menu, a running timer -, is a `GalleryLifetimeHints` of its sample; `librarySamples` fails for a class of the library with a meta object without a sample). A popup run by `exec()` is never an object on the stack whose parent the application can delete (`QPointer` + `new`, as `PDFMessageBox::showMessage`). Freed memory stays readable in a Release build on Windows, so these bugs pass the tests there - after a change of the lifetime code run the tests under valgrind (see *Build and test*).
- No lambdas in [Pdf4QtLibFluent/](Pdf4QtLibFluent/) unless truly unavoidable (they are hard to debug: no name in the call stack, no breakpoint by name, captures hide the lifetime): a connection is `connect(sender, &Sender::signal, receiver, &Receiver::slot)` to a member function (the receiver is always the context object, the slot gets the sender by its arguments or a member; `sender()` only when the signal does not identify the object, in a private slot, by `qobject_cast` with a null check), a comparator or a local helper is a static method of the class or of its `<Class>Helper`. A remaining lambda has a comment saying why it is needed, captures nothing by reference that may die before it runs, and a connected one has a context object. The allowed exception of the pointer-to-member form are the two string based `QMetaObject::invokeMethod` calls of the protected slots `commitData` / `closeEditor` of `QAbstractItemView` (`PDFShortcutDelegate::closeEditorOfView`). Tests and the gallery may use lambdas.
- The state of a `QPainter` is saved and restored only by a RAII guard, never by hand-written `save()` / `restore()` pairs: `PDFPainterStateGuard` ([pdfpainterutils.h](Pdf4QtLibCore/sources/pdfpainterutils.h)) in Pdf4QtLibCore and the libraries above it, `PDFStylePainterGuard` ([pdfstylepainterguard.h](Pdf4QtLibFluent/sources/pdfstylepainterguard.h), accepts a null painter) in Pdf4QtLibFluent, which does not depend on Core. A part of a function with its own state gets a nested block.
- `QT_NO_EMIT` is defined project-wide — signals are emitted with `Q_EMIT`, never `emit`.
- MSVC builds with `/W4`; keep new code warning-free (`/wd5054`, `/wd4127`, `/wd4702` are the only suppressions).
- User-visible strings must be translatable (`tr()` / `QApplication::translate`). `.ts` files under [translations/](translations/) are regenerated by the `PDF4QT_lupdate` target and normalized to CRLF by [cmake/NormalizeTsLineEndings.cmake](cmake/NormalizeTsLineEndings.cmake); do not hand-edit them.
- [SECURITY_TODO.md](SECURITY_TODO.md) collects security weaknesses found outside the scope of the current work (mostly Core, also the old applications) – add a found weakness there instead of fixing it ad hoc, they are solved together in a separate task.
- [NOTES.txt](NOTES.txt) tracks, section by section, where the implementation deliberately deviates from or does not yet implement the PDF 2.0 specification — check it before assuming a gap is a bug.
